# I/O 与资源预算

## 先判断哪里在等待

将读取/解码、CPU 处理、主机到设备传输、计算、输出分别观察。低 GPU 利用率可能来自小任务、同步、CPU 解码或 I/O，不能仅凭一个利用率数字增加 worker。优先利用程序已有计时和系统已有工具；没有工具时用小样本阶段耗时，不为诊断先安装大套件。

记录输入是本地 SSD、网络挂载还是对象存储，以及实际输出分区。只在长任务或大量文件场景检查 inode、临时空间和文件描述符；不为每个小脚本全套扫描。

## 并发与数据加载

- 遵守调度器/cgroup/容器分配，估算总线程数时包含各 worker 的 BLAS/OpenMP 线程；用任务级参数限制嵌套并发，不默认使用整机全部核心。
- 根据吞吐、CPU、RAM、共享内存和存储响应小步调整并发。网络盘和大量小文件可能因并发过高变慢。保持队列有界；生产速度超过消费速度时阻塞或限流，不无限囤积。
- PyTorch 多进程 DataLoader 的预取会放大驻留数据量。规划时可用 `worker数 × 每worker预取批数 × 每批主机内存` 作粗略下界，再加解码副本、队列、当前 batch 和数据集副本；这不是精确峰值公式。
- `num_workers=0` 时不设置多进程专用的预取/持久 worker 组合；具体允许参数按安装版本核对。IterableDataset 多 worker 要检查分片，避免重复样本。
- pinned memory 只在有相应设备传输需求并测得收益时启用，它会消耗主机资源；增加预取不等于增加 GPU 吞吐。
- 分块读取、顺序访问或复用已打开资源应保留原有数据顺序与结果要求。不要默认把整个数据集载入 RAM；不要为单次任务重打包全部数据。

## 文件、缓存和输出

为当前任务区分输入、正式产物、临时数据和缓存。已有项目目录约定优先；新目录用不覆盖已有内容的任务标识。记录临时文件归属，只有该任务明确产生且不再需要的内容才可清理。

按输入规模估计输出、checkpoint、缓存及临时双份写入需求，设任务预算而非固定“留10%空间”。预测可能耗尽磁盘时先减小当前任务的缓存上限或缩短试验，不删除用户历史数据。缓存键应反映输入版本和关键参数，防止旧结果被当成新结果。

需要避免半成品被误读时，将产物先写入同目录临时文件，成功关闭后替换；并发写入需要单写者、锁或各 worker 独立分片。原子替换的可见性不等于断电持久性，只有业务要求时才增加同步落盘措施。

长任务不要每 batch 打印大张量、保存图片或全量 checkpoint。使用已有的日志频率及保留配置；若要改变用户承诺的输出或删除旧 checkpoint，先说明影响。失败日志必须保留。日志要有容量/轮转方案，不能把磁盘当无限容量。

文件、数据库连接、HTTP 客户端采用明确的生命周期和异常清理；网络重试仅针对可重试且幂等的操作，设置总时限和次数。不要无限重试磁盘满或配置错误。

## 验证

检查处理数量、样本不重不漏、输出结构和必要的数值一致性。比较相同规模的 wall time、吞吐、峰值主机内存和输出增长；缓存导致的加速要单独注明。若分阶段计时本身改变流水线并行度，说明该局限。
