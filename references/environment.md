# 现有环境复用与增量补包

## 先发现，再运行

先读项目已有运行说明、依赖声明和已知成功命令，明确硬性版本要求与仅用于复现的推荐版本。依赖文件存在不代表必须立即整份安装；也不能忽略确实存在的 API/ABI 限制。

环境选择优先级：用户明确指定的环境 → 项目约定或已验证成功的环境 → 当前解释器 → 其他已有候选。检查当前解释器只是获取上下文，不赋予它选择优先权；明确指定的环境不兼容时先说明冲突，不静默换环境。对未指定的候选，满足要求即可复用，无需穷举。

按项目文件、启动脚本和当前 shell 的线索发现环境，只查询相关且已安装的工具，不逐一调用所有管理器或递归扫描整机：

| 环境来源 | 发现与复用要点 |
| --- | --- |
| conda、mamba、micromamba | 查询对应工具的已有环境和实际 prefix；注意不同安装位置或 root prefix 下的同名环境可能不同。micromamba 不依赖 conda 命令存在。 |
| venv、virtualenv、virtualenvwrapper | 检查项目 `.venv`/`venv`、已激活环境及项目记录的路径；名称只是线索，以实际解释器和关键依赖验证。 |
| uv、Poetry、Pipenv、PDM、Pixi | 读取项目声明、锁文件及工具的环境信息，定位已有项目环境。发现阶段不执行 install/sync，也不把可能自动建环境、下载解释器或同步依赖的 run 命令当作只读探测；执行时核对当前工具版本的复用方式与副作用。 |
| pyenv、asdf、mise 等版本管理器 | 核对项目版本文件和最终解析出的解释器；选中了 Python 版本不代表项目依赖已安装，仍需确认实际虚拟环境。 |
| Docker/Podman、Apptainer/Singularity、环境模块或 Nix 等 | 项目已采用时，检查既有运行上下文、镜像或环境定义及挂载/设备配置；在实际上下文内验证，不用宿主机包列表代替。不为探测自动拉镜像、构建或实例化新环境。 |

未列出的工具沿用同一原则：先识别项目使用方式，做只读发现，再验证并复用。远程项目在实际目标主机检查，本机环境不能代表服务器环境。不要激活或导入所有环境中的所有包。

对优先候选验证实际 `sys.executable`、Python 版本、关键包版本和导入，随后做一个不改变数据的最小功能检查。GPU 项目按需要检查设备是否可用及小操作，而不是仅看到安装了 torch 就认为可用。

沿用已验证的激活或执行方式。可以使用环境的明确解释器，但若项目依赖激活钩子、动态库路径或容器设置，须保留相应上下文，不能仅替换 Python 路径。在 tmux 中显式建立同一环境，不假定不同 shell 或不同工具调用继承上一次激活状态。记录管理方式、实际解释器、环境路径和关键版本。

## 缺包时只补缺口

用户的运行任务覆盖必要补包时可以直接补齐，无需每个包再问一次；遵循实际环境的权限要求。安装前确认是包缺失，而非解释器选错、导入路径错误、动态库故障或包名/模块名混淆。

- 在目标环境使用匹配的包管理器。pip 使用目标解释器的 `python -m pip`，避免裸 pip 指向其他环境；不改系统 Python 或默认 base 环境来方便运行。
- 保存相关现有版本，查看安装计划。工具支持时使用 dry-run/解析报告；不支持时先核对包元数据和依赖要求，不先升级包管理器来获得 dry-run。
- 默认保护所有已有包版本，特别是 Python、torch、torchvision、torchaudio、CUDA 相关运行库，以及项目依赖的 NumPy 和编译扩展。对 pip 或 uv pip 使用适当的版本约束和明确的目标解释器；对 conda/mamba/micromamba 等检查求解计划是否升级、降级、移除或更换现有包的构建。项目管理工具的补包同时检查依赖声明、锁文件和实际环境的变更，不以全量同步代替补缺口。即使版本号不变，核心二进制包被替换也需要审查。
- 允许安装确实缺少的新依赖及其缺失依赖，但选择与现有环境兼容的版本。不要默认 `pip install -U`、整份无约束安装 requirements 或 `conda update --all`。
- 不用 `--no-deps` 强压不兼容包；只有已核实其依赖全部满足时才考虑跳过依赖解析。不要交替使用多个包管理器反复“修复”同一个核心栈。
- 安装后检查新增包和原关键包的导入/版本及项目最小功能。检查依赖冲突时区分原有问题与此次引入的问题，不借机修复整个共享环境。记录新增内容；不自动卸载可能已被其他任务使用的包来假装回滚。

## 版本冲突的处理顺序

1. 先确认项目真正需要该版本，排除只因示例安装命令固定了新版本。
2. 在已有候选中选择兼容环境，或选择兼容当前核心栈的新增包版本。
3. 若使用项目已有的可选功能开关即可满足同一任务，可采用并说明；不跳过必要功能，不重写算法迎合环境。
4. 都不适用时，报告具体冲突及最小解决方式。优先考虑任务专用的隔离环境/克隆，保护现有环境，但只有现有环境确实不合适时才提出；创建前估算磁盘与下载成本，不自动复制巨大环境。
5. 若必须改变现有 Python、torch 等核心包版本或构建，先说明受影响环境、旧/新版本、兼容性和验证方案，在未有明确授权时取得同意。普通“把程序跑起来”不视为允许改动共享核心栈。

若目标环境正被其他任务使用，连新增包也可能影响它们（例如命名空间或动态库解析）；先判断变更是否会干扰运行任务，必要时等待或选择隔离方案，不停止其他任务。

## 轻量输出

例如：“复用 conda 环境 research；Python/torch 保持原版本；仅新增缺失包 X；关键导入与最小推理通过。”没有实际运行时标记为待验证。不要输出包含私有源凭据的完整安装配置。
