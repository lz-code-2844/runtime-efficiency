# 现有环境复用与增量补包

## 先发现，再运行

先读项目已有运行说明、依赖声明和已知成功命令，明确硬性版本要求与仅用于复现的推荐版本。依赖文件存在不代表必须立即整份安装；也不能忽略确实存在的 API/ABI 限制。

按相关性检查：当前解释器 → 项目指定的环境/项目内 .venv → 已知成功运行该项目的环境 → conda 等环境管理器列出的其他候选。可使用 `conda env list`、解释器路径和针对性包版本查询，不递归扫描整机，不激活或导入所有环境中的所有包。远程项目在实际目标主机检查，本机环境不能代表服务器环境。

对最可能合适的环境验证：实际 `sys.executable`、Python 版本、所需关键包版本和导入，随后做一个不改变数据的最小功能检查。GPU 项目按需要检查设备是否可用及小操作，而不是仅看到安装了 torch 就认为可用。候选满足要求即复用，无需穷举。

如果 `conda activate xxx` 后能正常运行项目，就沿用该环境。自动化执行可用该环境的明确解释器或合适的 `conda run`；在 tmux 中也显式指定环境，不假定不同 shell 或不同工具调用继承上一次激活状态。记录最终解释器、环境名/路径和关键版本。

## 缺包时只补缺口

用户的运行任务覆盖必要补包时可以直接补齐，无需每个包再问一次；遵循实际环境的权限要求。安装前确认是包缺失，而非解释器选错、导入路径错误、动态库故障或包名/模块名混淆。

- 在目标环境使用匹配的包管理器。pip 使用目标解释器的 `python -m pip`，避免裸 pip 指向其他环境；不改系统 Python 或默认 base 环境来方便运行。
- 保存相关现有版本，查看安装计划。工具支持时使用 dry-run/解析报告；不支持时先核对包元数据和依赖要求，不先升级包管理器来获得 dry-run。
- 默认保护所有已有包版本，特别是 Python、torch、torchvision、torchaudio、CUDA 相关运行库，以及项目依赖的 NumPy 和编译扩展。对 pip 使用适当的版本约束，对 conda 检查求解计划是否升级、降级、移除或更换现有包的构建。即使版本号不变，核心二进制包被替换也需要审查。
- 允许安装确实缺少的新依赖及其缺失依赖，但选择与现有环境兼容的版本。不要默认 `pip install -U`、整份无约束安装 requirements 或 `conda update --all`。
- 不用 `--no-deps` 强压不兼容包；只有已核实其依赖全部满足时才考虑跳过依赖解析。不要交替使用多个包管理器反复“修复”同一个核心栈。
- 安装后检查新增包和原关键包的导入/版本及项目最小功能。检查依赖冲突时区分原有问题与此次引入的问题，不借机修复整个共享环境。记录新增内容；不自动卸载可能已被其他任务使用的包来假装回滚。

## 版本冲突的处理顺序

1. 先确认项目真正需要该版本，排除只因示例安装命令固定了新版本。
2. 在已有候选中选择兼容环境，或选择兼容当前核心栈的新增包版本。
3. 若使用项目已有的可选功能开关即可满足同一任务，可采用并说明；不跳过必要功能，不重写算法迎合环境。
4. 都不适用时，报告具体冲突及最小解决方式。优先考虑任务专用的隔离环境/克隆，保护现有环境，但只有现有环境确实不合适时才提出；创建前估算磁盘与下载成本，不自动复制巨大环境。
5. 若必须改变现有 Python、torch 等核心包版本或构建，先说明受影响环境、旧/新版本、兼容性和验证方案，在未有明确授权时取得同意。普通“把程序跑起来”不视为允许改动共享核心栈。

若目标环境正被其他任务使用，连新增包也可能影响它们（例如命名空间或动态库解析）；先判断变更是否会干扰运行任务，必要时等待或选择隔离方案，不停止其他任务。

## 轻量输出

例如：“复用 conda 环境 research；Python/torch 保持原版本；仅新增缺失包 X；关键导入与最小推理通过。”没有实际运行时标记为待验证。不要输出包含私有源凭据的完整安装配置。
