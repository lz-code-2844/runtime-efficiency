# 长任务、tmux 与退出清理

## 启动契约

长任务使用独立 tmux 会话承载；若已有调度器或作业管理器，用其管理实际工作进程，tmux 承载提交/观察端，避免绕过资源分配。短命令不强制 tmux。

启动前检查该任务是否已有实例或有效作业 ID，避免重试启动产生重复任务。使用唯一会话名；只改当前会话选项，不改全局 tmux 配置。保存实际环境、工作目录、参数和必要日志，不导出整个含凭据的环境。

运行目录按现有约定保存足够恢复上下文的元数据：任务 ID、主机、命令、开始时间、会话/作业 ID、主进程身份；使用独立进程组时另记录 PGID/SID。PID 身份须结合启动时间与命令/工作目录，不能只存一个易被复用的数字。参数中的秘密脱敏。

主任务在 pane 内前台运行，避免 `&`、二次 daemonize、随意 `nohup` 使进程脱离。需要后台 worker 时必须有负责等待和关闭它们的父进程。启动器应在任务完成前等待，而非把“成功提交”当作完成。

启动器应保存真实退出码、结束时间与状态。重定向日志通常比增加 `tee` 管道简单；若确需管道，按实际 shell 正确保留工作进程退出码。异常或信号退出不得写成 success。正常结束退出任务专属 shell；不要为了保留日志而留一个永久 sleep。

## 子进程与资源所有权

优先复用项目已有的关闭逻辑、进程池和分布式 launcher，必要时做局部补充：在正常、异常和取消路径停止提交新任务，关闭队列/连接，等待自己创建的子进程，并释放线程池/进程池。具体关闭顺序依赖程序，不能用固定模板制造等待死锁。

避免子进程 stdout/stderr 管道无人消费而阻塞。长输出写日志或持续有界消费，不一次性收集无限输出。`wait`/`communicate`/`join` 用于不同对象，按程序实际机制回收；不能靠仅发送终止信号代替等待。

如果设计独立进程组，确认本任务的监督器与工作进程边界，不误把调用者、其他任务或共享 tmux server 纳入被终止范围。双重 fork、另起 session 或远程子任务可能逃离原进程组，应通过应用自身/调度器管理；不承诺一个 shell trap 可以消灭所有残留。

## 结束与取消

完成时依次核对：
1. 工作进程真实退出码、关键输出和应用级完成条件。
2. 该任务主进程、workers 和分布式 ranks 是否仍存活；核验 PID 身份及父子关系。
3. 该任务 GPU 进程/句柄是否已释放；共享设备上其他进程保留。
4. 保留运行记录和失败日志；只关闭属于该任务且不再需要的 pane/session。

退出码为0但任务自己的 worker 仍存活，记为“主任务完成、收尾未完成”。tmux 的 dead pane 可保留退出信息，它不是僵尸计算进程；会话消失也不证明所有后代都结束。

用户取消或已授权任务收尾时，先通过应用/launcher 的正常停止机制请求退出，再给合理且有界的等待时间。仍无响应才对核验属于本任务的进程/独立进程组发送终止信号；强制终止作为最后步骤，说明未落盘数据风险。每次升级信号前复核身份，避免 PID/PGID 复用；归属不确定时停止自动清理并报告。

绝不使用 `pkill python`、按用户名批量杀进程或 `tmux kill-server`。不要为了清一个 worker 重启共享服务、驱动或机器。

## 三种容易混淆的状态

- **真正僵尸（Z）**：进程已经退出，父进程未收取退出状态。不能通过再次 kill 该 PID解决，也通常不是显存占用来源。定位父进程的 wait/join 缺失；不贸然杀共享父进程。
- **活着的孤儿/残留 worker**：主任务结束后仍在运行，可能占 CPU、RAM 或 GPU。核验归属后通过原 supervisor/launcher 收尾；没有身份记录不能凭名字猜。
- **不可中断等待（常见 Linux D 状态）**：可能在等存储或内核 I/O。不是僵尸，重复 kill 不会解决底层等待；检查相关 I/O 并报告阻塞情况。

## 验证启动器或生命周期修改

只有新增/改动运行包装器或清理代码时，才需要有界验证：正常返回、非零退出、取消、带一个子进程退出，确认真实状态和无该测试所属残留。涉及进程组时同时放一个无关哨兵进程，验证其不被影响。测试只在隔离的临时目录和专属会话内执行，不使用真实训练任务做故障注入。

当前技能没有内置跨平台启动/杀进程脚本。未来增加此类脚本，必须通过上述行为验证后才能用于真实任务。实际长任务还没结束时，仅报告当前状态；没有持续观察能力时给出检查入口，不承诺已经完成收尾。
